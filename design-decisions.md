# WEX Purchase Transaction Service - Design Decisions

This document traces every significant design choice made in this service back to the
original requirements, shows the options that were considered, explains what was chosen
and why, shows the exact code that implements each decision, and demonstrates the
behavior with a curl command and its expected output.

## Decision 1: Unique Identifier Strategy

### Requirement
"When the transaction is stored, it will be assigned a unique identifier."
"Unique identifier: must uniquely identify the purchase."

### Options Considered

| Option | Notes |
|---|---|
| Auto-increment long (1, 2, 3...) | Simple, but sequential IDs leak record count and are easy to enumerate |
| UUID v4 (random) | Globally unique, no enumeration risk, no coordination between nodes |
| ULID | Sortable UUID alternative, adds complexity for no benefit here |
| Custom hash of fields | Non-trivial collision avoidance, no standard support in JPA |

### Choice: UUID v4, generated by JPA

UUID is globally unique by construction. No two transactions will ever share an ID, even
if the database is restored from backup, migrated, or a second instance is spun up. It also
prevents callers from guessing adjacent transaction IDs by incrementing a number.

### Implementation

```java
// PurchaseTransaction.java
@Id
@GeneratedValue(strategy = GenerationType.UUID)
@Column(name = "id", updatable = false, nullable = false)
private UUID id;
```

### Curl Demo

```bash
  -H "Content-Type: application/json" \
```

## Decision 2: Input Validation Approach

### Requirement
"Description: must not exceed 50 characters"
"Transaction date: must be a valid date format"
"Purchase amount: must be a valid positive amount rounded to the nearest cent"

### Options Considered

| Option | Notes |
|---|---|
| Manual checks inside the service method | Works but mixes infrastructure concern with business logic |
| Validation in the controller method body | Same problem, hard to test uniformly |
| Bean Validation annotations on the DTO | Declarative, runs automatically before the controller method body executes, standard |

### Choice: Bean Validation on the request DTO

Annotations on the DTO keep validation rules next to the fields they describe. Spring's
`@Valid` on the controller parameter triggers them automatically. The
`GlobalExceptionHandler` catches `MethodArgumentNotValidException` and returns structured
field-level error messages without any extra code in the service.

### Implementation

```java
// CreateTransactionRequest.java
@NotBlank(message = "Description is required")
@Size(max = 50, message = "Description must not exceed 50 characters")
private String description;

@NotNull(message = "Transaction date is required")
@PastOrPresent(message = "Transaction date must not be in the future")
private LocalDate transactionDate;

@NotNull(message = "Purchase amount is required")
@DecimalMin(value = "0.01", message = "Purchase amount must be a positive value")
@Digits(integer = 17, fraction = 2, message = "Purchase amount must be a valid monetary amount")
private BigDecimal purchaseAmount;
```

```java
// PurchaseTransactionController.java
@PostMapping("/transactions")
public ResponseEntity<TransactionResponse> createTransaction(
        @Valid @RequestBody CreateTransactionRequest request) {
    ...
}
```

## Decision 3: Purchase Amount Rounding

### Requirement
"Purchase amount: must be a valid positive amount rounded to the nearest cent"

### Options Considered

| Option | Notes |
|---|---|
| Rely on database column scale=2 to truncate | Truncation is not rounding; behavior is database-specific |
| Round in the controller | Mixes business rule into HTTP layer |
| Round in the service before persisting | Keeps rounding logic in the business layer, explicit and testable |

### Choice: Round in the service using HALF_UP, enforce at DB level as defense-in-depth

`HALF_UP` matches the common accounting convention: 0.5 rounds up. The DB column
`DECIMAL(19,2)` provides a second line of defense but the service guarantees what is
stored regardless of the database type used.

### Implementation

```java
// PurchaseTransactionService.java
@Transactional
public TransactionResponse createTransaction(CreateTransactionRequest request) {
    BigDecimal roundedAmount = request.getPurchaseAmount()
            .setScale(2, RoundingMode.HALF_UP);

    PurchaseTransaction transaction = PurchaseTransaction.builder()
            .description(request.getDescription())
            .transactionDate(request.getTransactionDate())
            .purchaseAmount(roundedAmount)
            .build();
    ...
}
```

```java
// PurchaseTransaction.java (DB column)
@Column(name = "purchase_amount", nullable = false, precision = 19, scale = 2)
private BigDecimal purchaseAmount;
```

## Decision 4: Persistence Layer

### Requirement
"Your application must be able to accept and store (i.e., persist) a purchase transaction"
"Please optimize the local environment setup process for an efficient developer experience"

### Options Considered

| Option | Notes |
|---|---|
| In-memory Map (no DB) | Data lost on restart, not production-ready |
| H2 in-memory mode | Fast for tests but data lost on restart in prod |
| H2 file-based | Persists to disk, zero setup, easy dev experience |
| PostgreSQL | Production-grade, requires a running DB instance to develop locally |
| MongoDB | Document store, adds complexity not needed for structured transactions |

### Choice: H2 file-based for development, JPA abstraction makes PostgreSQL a config swap

H2 in file mode means any developer can clone the repo and run the application with no
database setup. The JPA repository interface has no SQL - switching to PostgreSQL requires
only four property changes (datasource URL, driver, username, password) and adding the
driver dependency. No code changes.

### Implementation

```java
// PurchaseTransactionRepository.java
@Repository
public interface PurchaseTransactionRepository extends JpaRepository<PurchaseTransaction, UUID> {
}
```

```properties
# application.properties - default (H2 file, zero setup)
spring.datasource.url=jdbc:h2:file:./data/transactions;AUTO_SERVER=TRUE
spring.datasource.driver-class-name=org.h2.Driver
spring.jpa.hibernate.ddl-auto=update
```

To use PostgreSQL instead - only these four lines change:
```properties
spring.datasource.url=jdbc:postgresql://localhost:5432/wex_transactions
spring.datasource.driver-class-name=org.postgresql.Driver
spring.datasource.username=wex
spring.datasource.password=wex
```

## Decision 5: Exchange Rate Lookup Strategy

### Requirement
"Must use a currency conversion rate less than or equal to the purchase date from within
the last 6 months."
"If no currency conversion rate is available within 6 months... an error should be returned."

### Options Considered

| Option | Notes |
|---|---|
| Fetch all rates for the currency and filter in Java | Large payload, unbounded memory, slow for popular currencies |
| Fetch one page and iterate | Still depends on ordering and page size guesses |
| Push all constraints to the Treasury API query and fetch exactly one record | Single HTTP call, no in-memory filtering, deterministic |

### Choice: Server-side filter, sort, and page-size=1

The Treasury API supports date range filters, descending sort on `effective_date`, and
result count limits. Combining these three means the API does the work and returns exactly
the one record that satisfies the business rule. The service has nothing to filter.

### Implementation

```java
// TreasuryExchangeRateService.java
@Cacheable(value = "exchangeRates", key = "#countryCurrencyDesc + '_' + #purchaseDate")
public ExchangeRateData getExchangeRate(String countryCurrencyDesc, LocalDate purchaseDate) {
    LocalDate sixMonthsAgo = purchaseDate.minusMonths(6);

    String url = UriComponentsBuilder.fromHttpUrl(baseUrl + exchangeRatesPath)
            .queryParam("fields", "country,currency,exchange_rate,effective_date,country_currency_desc")
            .queryParam("filter",
                    "country_currency_desc:eq:" + countryCurrencyDesc
                    + ",effective_date:lte:" + purchaseDate.format(DATE_FORMATTER)
                    + ",effective_date:gte:" + sixMonthsAgo.format(DATE_FORMATTER))
            .queryParam("sort", "-effective_date")
            .queryParam("page[size]", "1")
            .build(false)
            .toUriString();
    ...
}
```

The URL this builds at runtime for a Canada-Dollar lookup on 2024-03-15:
```
https://api.fiscaldata.treasury.gov/services/api/fiscal_service/v1/accounting/od/rates_of_exchange
  ?fields=country,currency,exchange_rate,effective_date,country_currency_desc
  &filter=country_currency_desc:eq:Canada-Dollar,effective_date:lte:2024-03-15,effective_date:gte:2023-09-15
  &sort=-effective_date
  &page[size]=1
```

## Decision 6: Converted Amount Rounding

### Requirement
"The converted purchase amount to the target currency should be rounded to two decimal
places (i.e., cent)."

### Options Considered

| Option | Notes |
|---|---|
| Return the raw BigDecimal from the multiply | Could have many decimal places, non-compliant |
| Round with FLOOR | Loses a fraction of a cent every time, systematic bias |
| Round with HALF_UP | Standard accounting convention, required by spec |

### Choice: HALF_UP at two decimal places, applied after multiplication

### Implementation

```java
// PurchaseTransactionService.java
BigDecimal exchangeRate = rateData.getExchangeRate();
BigDecimal convertedAmount = transaction.getPurchaseAmount()
        .multiply(exchangeRate)
        .setScale(2, RoundingMode.HALF_UP);
```

### Curl Demo: Rounding in action

```bash

  -H "Content-Type: application/json" \
  -d '{"description":"Yen test","transactionDate":"2024-03-15","purchaseAmount":10.00}' \
  | python3 -m json.tool

# Retrieve with Japan-Yen (rate ~149.123 produces 1491.23 exactly)
curl -s "http://localhost:8080/api/v1/transactions/{id}?currency=Japan-Yen" \
  | python3 -m json.tool
```

Expected converted amount: `1491.23` (10.00 * 149.123, rounded HALF_UP to 2dp)

## Decision 7: Error Handling Strategy

### Requirement
"An error should be returned stating the purchase cannot be converted to the target currency."

### Options Considered

| Option | Notes |
|---|---|
| Return 200 with an error flag in the body | Non-standard, breaks HTTP semantics |
| Throw exceptions and return 500 for everything | Loses information, not actionable for clients |
| Centralized @RestControllerAdvice with HTTP status mapping | Standard Spring pattern, consistent error shape |

### Choice: @RestControllerAdvice with specific HTTP status per error type

- 400 for validation failures (bad input, client fix required)
- 404 when the transaction ID is not found (not stored or wrong ID)
- 422 when the exchange rate is unavailable (valid request, but conversion cannot happen)

### Implementation

```java
// GlobalExceptionHandler.java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(TransactionNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleTransactionNotFound(TransactionNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ErrorResponse(HttpStatus.NOT_FOUND.value(), ex.getMessage()));
    }

    @ExceptionHandler(CurrencyConversionException.class)
    public ResponseEntity<ErrorResponse> handleCurrencyConversion(CurrencyConversionException ex) {
        return ResponseEntity.status(HttpStatus.UNPROCESSABLE_ENTITY)
                .body(new ErrorResponse(HttpStatus.UNPROCESSABLE_ENTITY.value(), ex.getMessage()));
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidationErrors(MethodArgumentNotValidException ex) {
        Map<String, String> fieldErrors = new HashMap<>();
        ex.getBindingResult().getAllErrors().forEach(error -> {
            String fieldName = ((FieldError) error).getField();
            fieldErrors.put(fieldName, error.getDefaultMessage());
        });
        return ResponseEntity.status(HttpStatus.BAD_REQUEST)
                .body(new ErrorResponse(HttpStatus.BAD_REQUEST.value(),
                        "Validation failed: " + fieldErrors));
    }

    public record ErrorResponse(int status, String message, LocalDateTime timestamp) {
        public ErrorResponse(int status, String message) {
            this(status, message, LocalDateTime.now());
        }
    }
}
```

## Decision 8: Exchange Rate Caching

### Requirement (implicit)
"Please optimize the local environment setup process for an efficient developer experience
without compromising production readiness."

The Treasury API returns quarterly rates. The same currency + date combination will always
return the same answer. Calling the API on every retrieval is wasteful and adds latency.

### Options Considered

| Option | Notes |
|---|---|
| No cache | Correct, but every retrieval hits the Treasury API over HTTPS |
| Redis | Distributed cache, survives restarts, requires a running Redis instance |
| Caffeine (in-process) | Zero infrastructure dependency, bounded memory, TTL support |
| Ehcache | Similar to Caffeine, more configuration overhead |

### Choice: Caffeine with a 6-hour TTL, keyed by currency + purchase date

Since the rates are quarterly, a 6-hour TTL means any newly published quarterly rate is
visible within half a business day. The cache key combines currency and purchase date so
each distinct historical lookup is stored and served independently.

### Implementation

```java

@Cacheable(value = "exchangeRates", key = "#countryCurrencyDesc + '_' + #purchaseDate")
public ExchangeRateData getExchangeRate(String countryCurrencyDesc, LocalDate purchaseDate) {
    ...
}
```

```java
// TransactionApplication.java
@SpringBootApplication
@EnableCaching
public class TransactionApplication {
```

```properties
# application.properties
spring.cache.caffeine.spec=maximumSize=1000,expireAfterWrite=6h
```

## Decision 9: HTTP Client and SSL

### Requirement (implicit)
Production readiness - the service must connect to an HTTPS external API securely.

### Options Considered

| Option | Notes |
|---|---|
| Default Spring RestTemplate (no SSL config) | Works for public CAs but no timeout control |
| Trust-all SSL context | Disables all cert and hostname checks, security vulnerability |
| Apache HttpClient5 with default SSL + timeout config | JVM default trust store, full hostname verification, configurable timeouts |
| Apache HttpClient5 with pluggable truststore | Same as above, but also supports self-signed certs via config |

### Choice: Apache HttpClient5 with pluggable truststore, default to JVM trust store

The JVM default trust store covers all standard public CAs including the one used by the
Treasury API. The pluggable truststore allows teams running behind a corporate proxy with a
private CA to plug in their certificate without code changes.

### Implementation

```java
// AppConfig.java
@Bean
public RestTemplate restTemplate() throws Exception {
    SSLContextBuilder sslContextBuilder = SSLContextBuilder.create();

    if (StringUtils.hasText(trustStorePath)) {
        KeyStore trustStore = KeyStore.getInstance(trustStoreType);
        try (InputStream in = openTrustStore(trustStorePath)) {
            trustStore.load(in, trustStorePassword.toCharArray());
        }
        sslContextBuilder.loadTrustMaterial(trustStore, null);
    }
    // no trustStorePath = JVM default CAs, hostname verification stays on

    SSLContext sslContext = sslContextBuilder.build();

    CloseableHttpClient httpClient = HttpClients.custom()
            .setSSLSocketFactory(
                    SSLConnectionSocketFactoryBuilder.create()
                            .setSslContext(sslContext)
                            .build()
            )
            .build();

    HttpComponentsClientHttpRequestFactory factory =
            new HttpComponentsClientHttpRequestFactory(httpClient);
    factory.setConnectTimeout(connectTimeoutMs);
    factory.setReadTimeout(readTimeoutMs);

    return new RestTemplate(factory);
}
```

### To use a self-signed or private CA cert:

## Decision 10: Testing Strategy

### Requirement
"All functional automated testing you would include for a Production application should
be expected."

### Options Considered

| Option | Notes |
|---|---|
| Only unit tests with mocks | Fast, but never tests real HTTP or real Spring wiring |
| Only integration tests | Slow, heavy, mixes concerns |
| Three-layer approach: unit + slice + full integration | Each layer tests exactly what it owns |

### Choice: Three layers - unit (Mockito), web slice (@WebMvcTest), full integration (@SpringBootTest + WireMock)

WireMock stubs the Treasury API at the HTTP level. Tests run without network access, which
makes them reliable in CI and on machines without internet connectivity.

### Implementation overview

```java

    private RestTemplate restTemplate;

class PurchaseTransactionControllerTest {

// Integration - PurchaseTransactionIntegrationTest.java
// Tests the full path: HTTP in -> DB -> Treasury API stub -> HTTP out

@ActiveProfiles("test")
```

## Requirements Traceability

| Requirement | Decision(s) That Address It |
|---|---|
| Store a transaction with description, date, amount | Decision 2 (validation), Decision 3 (rounding), Decision 4 (persistence) |
| Description must not exceed 50 characters | Decision 2 (@Size(max=50)) |
| Transaction date must be a valid date format | Decision 2 (@NotNull + LocalDate deserialization by Spring) |
| Purchase amount must be positive, rounded to nearest cent | Decision 2 (@DecimalMin), Decision 3 (HALF_UP rounding) |
| Unique identifier assigned on storage | Decision 1 (UUID generated by JPA) |
| Retrieve transaction converted to target currency | Decision 5 (rate lookup), Decision 6 (converted amount rounding) |
| Use rate on or before purchase date, within 6 months | Decision 5 (filter=lte+gte, sort=-effective_date, page[size]=1) |
| Error if no rate available within 6 months | Decision 5 (empty response check), Decision 7 (422 status) |
| Converted amount rounded to 2 decimal places | Decision 6 (HALF_UP setScale(2)) |
| Production-ready | Decision 7 (error handling), Decision 8 (caching), Decision 9 (SSL), Decision 10 (testing) |
| Efficient local developer experience | Decision 4 (H2 zero-setup), Decision 10 (WireMock, no network needed) |
